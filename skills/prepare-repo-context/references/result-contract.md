# Query Result Contract

The same object is returned as `structuredContent` (and as compact JSON text) by the `repo-context` MCP tools; a tool call with `isError: true` carries the error message the script would have printed.

Every `query` invocation returns one JSON object. Read these fields before summarizing.

| Field | Meaning | What to do |
|---|---|---|
| `status` | `ready`: the search examined everything it needed (this also covers results with more matches than `--maximum-results`, where `truncated` is `true` with a counted `omitted_count`). `partial`: two unrelated causes, told apart by `next_safe_action`. With `next_safe_action: use-index`, the *index* has incomplete coverage (parse failures or extraction limits at build time); findings are complete for what was indexed. With `next_safe_action: refine-query` and warning `query-frontier-exhausted`, a work budget stopped the *search*; results may be missing. `stale`/`error`: the index does not match the worktree. `stale` from `query` now means only a refusal the broker could not repair; follow the error message (`run prepare inspect` or `run prepare build --confirm-state-write`). `stale` with `next_safe_action: update-index` and no findings means the request named an identity the operation cannot use for that purpose — for example a `related-symbols --result-id` that is not a `definition`, `module`, or `entry-point` record, or a `source-snippets`/`related-symbols` identity naming a `reference` record. | `partial` + `use-index`: answer normally; mention once that coverage is partial (some files were not indexed). `partial` + `refine-query`: say results may be incomplete and narrow with a filter or fall back to `grep`. `stale` + `update-index`: re-run the query that produced the identity and use a fresh one; do not retry the same identity. On any other `stale`, run `inspect` and follow `next_safe_action`. |
| `freshness` | `exact` binds the index to the current commit and dirty state. Anything else is not current. | Only `exact` results may be described as current. |
| `truncated` | `true` when the finding list is known to be incomplete for any reason: more matches than `--maximum-results`, the output budget trimmed findings, or the search was exhausted. | Tell the user the list is a prefix. |
| `omitted_count` | Omissions the engine actually counted (ranking overflow and output trimming). It is `0` when the engine could not count what it missed; `truncated` is still `true` then. | Never present `omitted_count: 0` as proof of completeness when `truncated` is `true`. |
| `warnings` | Codes such as `python-dynamic-lookup` (a file uses `getattr`/`eval`/dynamic imports; its literal definitions are still verified) or `query-frontier-exhausted` (a budget stopped the search). | Mention warnings that affect the answer; do not list them all. |
| `next_safe_action` | `use-index`, `refine-query`, `rebuild-index`, `update-index` (a `query` result never returns `build-index` or `install-native-engine`; the broker refuses to query without a ready context, so those two come from `inspect`, `build`, and `activate`). | Follow it; never invent another action. A `build` or `activate` answer carrying the warning `incompatible-generation` removed an index an older runtime had written (that runtime is named in `engine.replaced_generation_version`) before rebuilding, so report the rebuild rather than an error, and run the build once more if it still answers `rebuild-index`. |
| `refresh` | `{performed, changed_path_count, duration_ms, pruned_generation_count}`. `performed: true` means the index was brought to the current commit and dirty state before the search; `pruned_generation_count` is how many superseded index generations this call removed (`0` when none were old enough, or when the current generation is itself younger than the grace period), reported after every `build`, `activate`, and query, not only after a refresh. | Do not report it unless it affects the answer's timing; `performed: false` needs no mention, and neither does `pruned_generation_count: 0`. |
| `base` | Present only on `changed-symbols` and `impact-candidates`: `{requested, ref, sha, source, warning}` for the base the change set was measured against. `source` is `explicit`, `upstream-main`, `origin-head`, `local-main`, `local-master`, `unknown`, or `staged` (the index against `HEAD`, what `git commit` would record, with untracked and unstaged edits excluded). `staged` bounds the change set, not the resolution: the records those ranges select come from the indexed working tree, so a partially staged file can attribute a hunk to the symbol at those lines in the working-tree copy. | Name the base you actually compared against. When `warning` is `base-unresolved`, say the answer covers uncommitted changes only. |

## Findings

Each finding has `rank`, `result_identity`, `path`, `start_line`, `end_line`, `language`, `record_kind`, `qualified_name`, `evidence_class`, and `preview`.

- `evidence_class` is `verified` when the extractor proved the record from a literal token in the current source, `inferred` otherwise (hidden unless `--allow-inferred`). Never upgrade it in prose.
- `preview` is one sanitized line: the first line of the record's range for functions, classes, and methods (for a decorated Python definition that is the decorator line); the first body line under a heading. It is a display hint for choosing the right result. It is not evidence; quote source only from `source-snippets`. A heading directly followed by another heading has an empty preview.
- A `source-snippets` result that is `partial` with `returned_count` 0 and `omitted_count` 1 means the snippet did not fit the output budget: ask again with a larger budget (`--maximum-output-characters 8000` or `12000` for the script, `maximum_output_characters` for the tool).
- `record_kind` tells you what matched: `definition`, `import`, `module`, `entry-point`, `configuration` (a key name), `heading`, `document-chunk`. Within a match tier, findings are ordered: definitions, modules, entry points and headings first; configuration keys and document chunks next; imports last; then by path.

## Relationship findings (`related-symbols`)

A `related-symbols` finding carries four extra fields beyond the ones above: `relation` (`call` or `import`), `edge_evidence` (`verified` or `inferred`), `reference_line`, and `reference_count`. `repository-map`, `search-symbols`, `search-docs`, `source-snippets`, and `repository-overview` findings do not carry these keys at all, so do not look for them there. `changed-symbols` findings carry the keys but describe no edge: `relation` and `edge_evidence` are `null` and the two counters are `0`. An `impact-candidates` candidate carries them filled from its strongest anchor (see below).

- `edge_evidence: verified` means the resolution from the reference to this specific record was unambiguous (same module scope, or through a single matching import). `edge_evidence: inferred` is a **name match, never proof** — the engine found a definition with the right name somewhere in the index but could not prove it is the one actually called. `related-symbols` hides `inferred` edges by default; only `--allow-inferred` (`allow_inferred` over MCP) returns them, and you must still present them as unconfirmed, not as fact.
- `reference_line` is the source line of the call or import that produced this edge. `reference_count` is how many times that same target name is referenced from the same enclosing symbol (merged occurrences, not a count of distinct call sites elsewhere).
- A `callers` finding for a bare module-level call (outside any function, class, or method) is synthesized with `record_kind: module`; its `result_identity` belongs to the underlying `reference` record, and `source-snippets` refuses it by design (a `reference` identity is never snippet-able). Report the finding's `path` and `start_line` directly instead of fetching a snippet for it.
- The summary object's own `schema_version` field stays `"1"` for every operation, including `related-symbols` — it names the broker's envelope shape, not the four relationship fields, which are carried on the findings regardless of that value.

## Change findings (`changed-symbols`)

A `changed-symbols` finding is an ordinary finding of `record_kind` `definition`, `entry-point`, or `module` whose line span meets a changed hunk of its path. Findings are ordered by `evidence_class` (verified before inferred), then by path, then by start line. `output_characters` is the rendered character count the engine reports, exactly as for the other engine operations.

- Only Go files carry a `module` record (it spans the package clause); a Python file has none, so a changed Python module shows up through its changed definitions.
- These change-set warnings mean the answer covers less than the change set, or was compared against something other than what was asked: `base-unresolved` (no base could be resolved, so only uncommitted changes are covered), `changed-diff-unavailable` (the difference could not be read, so the answer is empty), `changed-path-not-indexed` (the change set reached a path the index carries no record for — a deleted file, or a file outside the indexed set), `changed-path-unsafe` (a path the index could not accept was dropped), `changed-paths-limit` (more than 200 changed paths, so the tail was dropped), and `changed-selector-limit` (the request frame was too large, so paths were dropped from the tail). Say which of them applied.
- These two only cost precision, never coverage: `changed-ranges-collapsed` (a path with more than 64 hunks is treated as changed as a whole) and `changed-selector-collapsed` (the request frame was too large, so the path with the most hunks is treated the same way). They can add symbols of that path that a hunk did not touch.
- A deletion is attributed to the surviving adjacent line, so the enclosing definition counts as changed. A whole deleted file has no record left and appears only as `changed-path-not-indexed`.

## Impact candidates (`impact-candidates`)

`impact-candidates` is composed by the script from one `changed-symbols` answer plus one `related-symbols` call per changed symbol and direction (`callers` for a changed definition or entry point, `importers` for a changed module or definition), so its result adds fields the engine operations do not have:

| Field | Meaning |
|---|---|
| `changed` | The change set itself: `result_identity`, `path`, `start_line`, `end_line`, `record_kind`, `qualified_name` per changed symbol, or the compact `path`, `qualified_name` when the budget made the layer shrink — the identity is still available from `changed-symbols` and from every candidate's `anchors`. Ordered with every entry that anchors a returned candidate first (most-anchored first, then by path and start line), then the rest (non-test paths before test paths, a caller-anchor kind — `definition`/`entry-point` — before `module`, then by path and start line). Every anchor named by a returned candidate is guaranteed to appear here, whatever the budget trimmed. |
| `changed_count` | How many changed symbols the composition followed (at most 64). |
| `changed_omitted_count` | Changed symbols the engine left out of that set, counted separately from `omitted_count`, which adds them to the omissions of the relationship calls and to the candidates dropped for the budget. |
| `changed_trimmed_count` | Changed symbols the output budget dropped from the tail of `changed`, so the length of the list plus this count is always `changed_count`, the change set the engine returned. `0` when the list is whole. |
| `findings` | The candidates: one entry per related record, never a changed symbol itself. |
| `anchors` | On each candidate, the changed symbols it depends on: `result_identity`, `path`, `qualified_name`, `relation`, `edge_evidence`, `reference_line`, `reference_count`, strongest evidence first. The candidate's own four edge fields are copied from the first anchor. |

- Candidates are ordered by `edge_evidence` (verified before inferred), then by number of anchors, then by path and start line, so a truncated list is the strongest prefix, not a sample. `inferred` edges appear only with `--allow-inferred`/`allow_inferred`, and the composition never upgrades an edge.
- `--maximum-results` (`maximum_results` over MCP) defaults to 16 here, not the 8 most other operations use: the candidates are what this operation was asked for, not context alongside them, and the output budget already bounds what the answer carries.
- `status` is `ready` only when every underlying call was ready; otherwise it is `partial` with that call's `next_safe_action`. `warnings` is the union of every underlying answer's warnings plus the change-set warnings above.
- `output_characters` is the serialized length of this object, which is a different measure from the engine's rendered-text count on the direct engine operations. `repository-overview` is measured the same way as this one; every other operation reports the engine's count.
- The two layers share the output budget and neither pays for the other, cheapest loss first, in these five steps: (1) an object inside the budget is returned as is, `changed` entries in full; (2) an object over budget shrinks every `changed` entry to the compact `path`, `qualified_name` right away — not only once the list itself is over its third of the budget, since losing entry detail is cheaper than losing a candidate, and the line range, the record kind, and the identity are one `changed-symbols` query (or a candidate's `anchors`) away; (3) a compact list still over that third drops entries from the tail, counted in `changed_trimmed_count` with the warning `changed-list-trimmed` — except an entry that anchors a returned candidate, which this step never removes; if the anchors alone still exceed the third, they are kept anyway and the object carries the overage into the next step; (4) candidates then drop from the tail (`truncated`, `omitted_count`) until the whole object fits — dropping a candidate can free the changed entries that anchored only it, so step (3)'s protection is re-evaluated once every candidate that is going to be dropped has been, and the changed layer only then gives up entries that no longer anchor anything; (5) only an object that does not fit with no candidate and no changed entry left carries the warning `output-budget-exceeded`. The anchors of a kept candidate are never trimmed, so every reported candidate keeps its full attribution and still names the changed symbols it depends on even when the `changed` list lost them. Once those steps settle, whatever of the output budget still went unspent is given back to the `changed` list: entries steps (3) and (4) dropped are restored, in the order they were retained, for as long as the whole object still fits, so `changed_trimmed_count` and `changed-list-trimmed` only ever report what genuinely could not fit.
- A candidate is a symbol that references something you changed, not a defect. Report it with its anchors and the edge's evidence, and never state that it breaks.

## Commit-time hook (`hook run`)

`hook run` is what an installed `pre-commit` launcher calls. It asks one `impact-candidates --staged` query and writes at most one short report to stderr: a header, at most five detail lines, and at most one trailer (addendum D16). It never writes to stdout and always exits 0, whatever it finds or fails to find.

```
TAF impact: 3 files depend on this change and are not in this commit
  tools/taf-context/taf_context/impact_hook.py:467  <- context_operations.PrepareCLIError
  tools/taf-context/taf_context/mcp_server.py:13    <- context_operations.PrepareCLIError
  tools/taf-context/taf_context/prepare_cli.py:162  <- context_operations.PrepareCLIError
  ... plus 2 test files (ask your agent to list TAF impact for this commit)
```

- **Header:** `TAF impact: N file(s) depend(s) on this change and are not in this commit`, `N` counting the untouched **production** files; `N+` when the result is truncated (the engine omitted candidates). When no production file depends but test files do, the header counts the test files instead (`TAF impact: 3 test files depend on this change and are not in this commit`) and the detail lines list them — a test that references the changed symbol is still a legitimate warning when nothing else does. When nothing depends, nothing is printed.
- **Detail lines:** two-space indent, `<path>:<reference_line>`, padded so the `<-` column aligns across the printed lines, then `<- <anchor qualified_name>`. At most five, production files first (candidates are grouped by `path`, keeping a call representative over an import one, then printed non-test files before test files, each group in the composition's own candidate order — edge evidence, then anchor count, then path and start line; see Impact candidates above). Test files are printed only when no production file was.
- **Trailer:** one indented `... ` line, present when anything was left out: remaining production files R and test files T (T counts all untouched test files when production lines were printed) — `... and R more, plus T test files (…)`, `... and R more (…)`, `... plus T test files (…)`; when truncated, a `+` marks whichever count the engine's omission makes uncertain — `R+` when production files remain, or `T+` when R is 0 and only the test count is left to name (and a tests-only header reads `N+ test files depend …`); `... and possibly more (…)` when R is 0, T is 0, and the result is truncated. The parenthesis is always `(ask your agent to list TAF impact for this commit)` — a redirection to the surface that can show the full list (MCP `impact_candidates`, `staged: true`), not a command; `query impact-candidates --staged` is not runnable in a plugin installation (no `prepare` on PATH).
- **Colour:** only the header, only when `stderr.isatty()` is true, `NO_COLOR` is unset, and `TERM` is not `dumb` — bold (`ESC[1m … ESC[0m`). Everything else is plain; a non-TTY stderr (GUI clients, CI, pipes) gets pure ASCII with no escape codes.
- **Grep stability:** every header starts with `TAF impact:`; every detail and trailer line starts with two spaces; the verbose diagnostics keep their own `TAF hook:` prefix.
- The hook chooses its report from the complete candidate set; it never trims the answer for output, and the composition's own result cap is set so it can never bind either (the query's own output-character budget and its `maximum_results` are both sized so neither the shared trim nor the composition's own slice ever cuts the set the hook counts from). What remains is complete as far as the engine returned it: a symbol with more than 64 references in one direction, or a change set of more than 64 changed symbols, can still leave dependents the composition never saw - exactly what the `+`/"possibly more" marker reports.
- "Untouched" means the candidate's own `path` is not in the staged change set (`git diff --cached --name-only` against `HEAD`) — a dependent inside the commit is already handled and never named.
- Only `edge_evidence: verified` candidates are ever considered; the hook never guesses from an inferred edge.
- The hook stays completely silent (no line at all) when: `inspect`'s `next_safe_action` is anything but `use-index` (including the native engine not being installed); the staged change set has no untouched dependents; `TAF_HOOK=0` is set in the commit's environment; the hook has waited its 3 seconds for the answer and gives up (process cleanup may add a moment on top of that wait); or any error is raised while answering. `--verbose` explains a silent run with one line of its own, prefixed `TAF hook: <reason>` (a different prefix from the report above), on the same stderr.
- The hook is deliberately not interactive: a prompt inside pre-commit would hang GUI clients (no stdin), CI (no TTY), and an agent's own commits; questions about the full list go to the agent afterwards, not to a prompt.

`hook install` and `hook remove` write the launcher and, like every `prepare` command except `hook run`, refresh the pointer under TAF's state when that state exists; `hook status` reads the launcher and performs the same standing-consent incremental refresh as `inspect`. None of the three builds, activates, downloads, or removes anything. The hook is available on macOS and Linux — the launcher is a POSIX `sh` script — and `install` and `remove` refuse elsewhere with `the commit-time hook is available on macOS and Linux only`; `status` still reports, and `--staged` and the queries themselves are unaffected.

The launcher follows the broker that last ran on this machine instead of trusting only its own embedded, install-time paths: every `prepare` command but `hook run`, `hook install` itself, and the bundled MCP server at startup refresh a small pointer file, `<state root>/hook/launcher-target` under TAF's user-local state — two lines, the resolved interpreter and the plugin's entry-point script — atomically, mode 0600 in a 0700 directory, and only when its content differs and the state root already exists (an `inspect` before any `build` still creates nothing). Writing it is a convenience: every failure is swallowed, and it is never a reason a command fails. `hook run` never writes it, so a stale broker recorded once can never re-assert itself through a later commit. At commit time the launcher reads the pointer first; when it is readable and names an existing script, that interpreter and script run instead of the embedded ones. Otherwise, or when the pointer is missing entirely, the embedded paths are the fallback; when the chosen interpreter is not executable, `command -v python3` is tried; when no interpreter or no script can be found, the launcher stays silent and the commit proceeds, exactly as when the index is not ready. The pointer file lives in the user's own state directory (mode 0700) — the same trust level as the launcher itself in the user's `.git/hooks`, both user-writable local files.

- `hook status --repo <repo>`: `{"schema_version": "1", "mode": "hook-status", "hook": "installed" | "foreign" | "absent" | "redirected", "hooks_path": <str>, "hook_path": <str or null when redirected>, "chained": <bool>, "launcher_current": <bool or null>, "launcher_text_current": <bool or null>, "launcher_generation": "pointer" | "embedded" | null, "posix": <bool>, "readiness": {"next_safe_action": <str or null>, "error": <str or null>}}`. `launcher_current` means the installed launcher runs this plugin's broker: `true` when its text already matches what `install` would write now, or when it is pointer-aware (carries the `taf_target=` line of the self-healing template) and its pointer file names this plugin's entry script and an executable interpreter; `false` otherwise - and re-installing fixes it; `null` when nothing is installed or the state root cannot be resolved (the pointer path is unknown). `launcher_text_current` is the older, stricter text comparison alone: `false` only says the embedded fallback predates the current install (a plugin update, or a hook manager's own block appended after TAF's) - a re-install refreshes it, but it is never required for the hook to be current. `launcher_generation` is `pointer` for the self-healing template every current install writes, `embedded` for an older TAF launcher that predates it, `null` when nothing is installed. `posix` is `false` on a platform where `install` and `remove` would refuse. `readiness` is the same `next_safe_action` an `inspect` would report, with `error` carrying its message instead when that call itself fails.
- `hook install --repo <repo> --confirm-hook-write [--chain]`: `{"schema_version": "1", "mode": "hook-install", "hook_path": <absolute launcher path>, "written": true, "chained": <bool>, "chained_hook_path": <absolute path or null>, "launcher_current": true, "interpreter": <str>, "script": <str>, "next_safe_action": "none"}`. `launcher_current` is always `true` here: the launcher just written and the pointer just refreshed agree by construction. A chained hook that runs decides the commit with its own exit code, so a failing one still blocks it; one that cannot be run at all (deleted, or no longer executable) is skipped and the commit proceeds. `install --chain` refuses a foreign hook that is not executable, since git was not running it either.
- `hook remove --repo <repo> --confirm-hook-write`: `{"schema_version": "1", "mode": "hook-remove", "hook_path": <str>, "removed": <bool>, "restored": <bool>, "next_safe_action": "none"}`. `restored: true` means a chained hook moved aside by `install --chain` was put back at `pre-commit`.

## Overview (`repository-overview`)

`repository-overview` answers in two layers: `groups`, a directory table sized by the output budget, and the usual `findings`, a ranked file layer selected from those groups. The table is the first layer of the answer — read it before the files.

| Field | Meaning |
|---|---|
| `groups` | One row per directory group: `path_prefix`, `depth`, `file_count`, `definition_count`, `entry_point_count`, `document_count`, `configuration_count`, `languages` (`{language, file_count}`, most files first, then by name), and `representative_identity`. The table has no fixed width: how many rows it carries is what the output budget allowed. |
| `entry_point_count` | How many of the group's **files** the repository can be started at, not how many entry-point records they hold: a file counts once if it carries an entry-point record (a `main`-shaped definition) **or** if its base name is one the ecosystem starts at. A file that answers to both rules still counts once. |
| `path_prefix` | Always relative to the repository root, never to the described subtree: `.` for the files sitting at the root, `<directory>/` for a directory, `<directory>/.` for the files sitting directly inside a directory the table split, and `*` for the row the directories that did not fit the budget were folded into. |
| `depth` | Directory segments below the overview root; `.` and `*` are `0`. |
| `representative_identity` | The identity of the representative record of the group's top-ranked file — an ordinary identity `source-snippets` accepts. It is `null` for `*`, which sums several directories and stands for none of them. |
| `overview` | `{root, counted_file_count, other_group_count}`: the subtree the table describes (`""` for the whole repository, otherwise a prefix ending in `/`), how many files it counted, and how many directories the `*` row folds together — `0` when the whole table fits. |

- How the table is shaped: one group per top-level directory under the root, plus `.` for the root's own files. A group holding more than 40 % of the counted files is replaced by its children, repeatedly, while it stays within four segments of depth; a group whose only child is one directory is replaced by that directory and the descent goes on from there, so an intervening `all/` or `src/main/` segment never stands for a subtree on its own. No fixed count stops that split. The rows are then ordered by definition count, then file count, then prefix, and the tail is folded into `*` — counts summed, languages merged — until the table fits its share of the output budget. A `*` row therefore means directories are missing from the table, never that files are missing from the counts; a table with no `*` row is the whole table.
- A file is counted once, with the language most of its records are written in, and only if it carries at least one record the query admits: a file whose records are all `inferred` is counted only with `--allow-inferred`. `document_count` and `configuration_count` count files that carry nothing but prose, or nothing but configuration keys; one definition inside a document makes it code again. Only Go files carry a `module` record, so a Python package shows up through its definitions.
- The file layer ranks each group's files in tiers — entry points and the well-known entry file names first, then the files that define something, then documents with a README ahead of the rest, then configuration, then whatever is left. The well-known names are the ecosystems' own entry files (`main.go` under a `cmd/` directory, `main.py`, `__main__.py`, `app.py`, `manage.py`, `cli.py`, `index.js`, `index.ts`, `index.tsx`, `server.ts`, `main.rs`, `lib.rs`) and the conventions of a framework whose routes are its directory tree: the Next.js App Router conventional file names (`page`, `layout`, `route`, `loading`, `error`, `not-found`, `template`, `default`, in `.tsx`, `.ts`, `.jsx` and `.js`), matched by base name wherever the file sits, and its four single-file conventions (`middleware.ts`, `instrumentation.ts`, `sitemap.ts`, `robots.ts`). That list is a ranking hint and nothing more: such a file keeps the `record_kind` it really has, and being called `main.py` never makes a record an `entry-point`.
- How the file layer is selected: every group offers its entry-point files first, in table order, before any group offers a second-tier file — so an App Router `app/` directory leads the answer even when two larger directories head the table. The round-robin then resumes, one file per group per round in table order, so a dominant directory cannot fill the answer on its own. `--maximum-results` bounds the entry-point round as well as the rest. Each finding is one representative record of its file, the same shape as a `repository-map` finding.
- `omitted_count` is the counted files the answer does not list, so `returned_count` plus `omitted_count` is `overview.counted_file_count`, and `truncated` is `true` whenever a counted file was left out — which is normal here, since the table describes far more files than the file layer lists.
- `output_characters` is the length of this object's canonical JSON, the same measure as `impact-candidates` and not the rendered-text count the direct engine operations report.
- The output budget is the only size knob, and the two layers share it: neither takes more than half of it while the other still wants room. A table wider than its half folds its tail into `*` until it fits that half, down to a single directory row; a table already inside its half is handed on whole. Whatever the table did not spend is the file layer's, and the file layer then drops from its tail until the whole answer fits. Only a one-row table with no findings at all reports `output-budget-exceeded`. So a wider budget buys a wider table **and** more files, and a narrower one keeps the counts while losing the detail behind them. The table alone can use most of a 4000-character budget, which is why this operation defaults to 8000 characters on both surfaces rather than the 4000 the others use; `--maximum-output-characters 12000` widens it further, and `--path-prefix D/` is the way to go deeper into one subtree instead of wider over all of them. `--maximum-results` (`maximum_results` over MCP) also defaults higher here, to 24 rather than the 8 most other operations use, since the file layer is a repository-wide sample rather than a search result and its findings carry no relationship keys to spend the budget on. (`impact-candidates` also defaults above 8, to 16, for its own reason — see that section.)
- `--path-prefix` names whole directory segments for this operation, unlike `repository-map`, which matches any path prefix: `--path-prefix tools/` describes that subtree, while a file path or a partial segment answers with an empty table and `counted_file_count: 0` rather than an error, carrying the warning `overview-root-not-a-directory` — which is what tells a root that names no directory apart from a directory nothing was counted in. Several prefixes are not composed either — the first in sorted order becomes `overview.root` and the warning `overview-root-first-prefix` says so.
- On a repository with more indexed paths than the map frontier admits, the answer is `partial` with `next_safe_action: refine-query` and the warning `query-frontier-exhausted`. The table was then built from the paths the frontier reached in path order, so the counts and the shares that shaped the rows describe that part of the repository rather than all of it: say so, and describe one subtree at a time with `--path-prefix`.

## Presenting results
